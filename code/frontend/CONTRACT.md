# Member One presentation contract

This frontend consumes Member Two's shared `CaseResult` structure. The exact TypeScript fields are in `src/types.ts`. The engine, deletion-policy logic, email sender and challenge CSV writer remain Member Two's responsibility.

For the first frontend milestone, `GET /api/cases` returns an array of full case results, including `graph_data: { nodes, edges }`. The shared contract did not specify whether this route returns summaries or full results; this is a proposed transport convention to confirm at integration. If the backend returns summaries, adapt `src/api.ts` to fetch `GET /api/cases/{case_id}` before rendering a detail. Do not duplicate engine logic.

Required shared fields: `case_id`, `deletion_status`, `summary`, `identities`, `findings`, `steps`, `evidence`, `graph_data`. The presentation fields inside identities, findings, evidence, and graph nodes are provisional because the supplied shared contract left those arrays untyped. Optional `request` adds `email`, `requested_at`, `audit_at`, `reported_status`, and `request_text`. Missing request metadata is shown as not supplied. Supply already masked identifiers for display; raw identifiers should not be sent unnecessarily.

The graph renders only supplied nodes and edges whose endpoints exist. Node statuses are `VERIFIED`, `ISSUE`, `PENDING`, `CONNECTED`; these are visual classifications, not challenge output statuses. There is no engine inference in the graph component. Finding `resource_id` should match a graph node ID for path highlighting. `evidence_ids` on nodes refer to `evidence[].id`.

`summary` describes the authoritative investigation. Overview metrics derive from the actual loaded cases. `COMPLETE`, `INCOMPLETE`, and `NOT_APPLICABLE` preserve the challenge enumeration. Verification success here means the percentage of applicable cases whose audit status is COMPLETE, not a fabricated step execution rate.

Set Vite's API URL once in `.env.local`. The FastAPI presentation service must permit the local origin `http://127.0.0.1:5173` (and `http://localhost:5173` if used). Failed live requests surface errors and never silently fall back to fixtures.

Slack and email are visibly unavailable until their server endpoints exist. No webhook or provider key belongs in Vite configuration. The frontend currently sends no notifications, approvals, email, or deletion actions. Email endpoint paths, authorization, approval models, revisions, and delivery statuses must be agreed with Member Two before wiring those controls. Remediation and future verification are recommendations, not executed operations.

Demo fixtures are fictional and isolated in `src/data.ts`; their `DEMO-*` IDs do not map to dataset cases. They must never be used to write root `output.csv`.

## 3D presentation

The renderer positions identity nodes centrally and distributes supplied nodes deterministically in three dimensions. Positions and the nonselectable spherical guide have no policy meaning. No edges or alert statuses are generated by the renderer. It ignores edges with missing endpoints, highlights supplied ancestry with a cycle-safe traversal, and binds evidence/remediation to the selected resource or system's supplied findings. Directional particles are limited to relationships attached to resources with a supplied REPORT_ACTIVE_DATA_FLOW finding.


## Phase 1 local API and Slack

`python code/server.py` exposes `GET /api/cases`, translating Member Two's unmodified `CaseAuditResult` into this presentation shape. Decisions and ordered steps remain unchanged; identity labels and free-form reasons are excluded. Notification severity is only a presentation mapping: remaining records, exposed identifiers and active flows are HIGH; restore risk is MEDIUM; an incomplete case without classified findings is UNKNOWN. Complete/non-applicable cases without findings use NONE.

`GET /api/session` creates a one-hour local session with an HttpOnly, SameSite=Strict cookie and returns a CSRF token plus a configuration boolean. It never returns the webhook. `POST /api/cases/{case_id}/slack` requires that cookie, `X-CSRF-Token`, an allowed local Origin, JSON content type and an empty `{}` body. Cases are looked up in the server's engine results, never accepted from the browser. Demo IDs are rejected. HTTP 200 `{ "status": "sent", "case_id": "..." }` is returned only after Slack responds `200 ok`. Errors: 400 invalid request, 403 protection/session failure, 404 unknown case, 409 duplicate/in-flight send, 429 rate limit, 502 unconfirmed/rejected delivery, 503 missing/invalid configuration.

The API binds only to 127.0.0.1 and permits the local Vite origins on ports 5173 and 4173. This is protection for the local Phase 1 application, not a public multi-user authentication service. Vite dev and preview proxy `/api` to port 8000; leave `VITE_API_BASE_URL` empty. Explicit local API origins also support credentialed CORS for the allowlisted frontend origins. No automatic delivery retries occur. Duplicate successful sends for a case are blocked for 30 seconds in memory; the limit resets on server restart.

The Slack payload contains a validated internal case ID, engine status, operation-derived severity, its qualification and a private Slack link to the sanitized full HTML report. No names, email/phone/hash values, resource identifiers, request text, raw evidence, free-form reasons or credentials are sent. Affected systems are allowlisted; unknown values become Unlisted system. The channel is fixed by the Incoming Webhook's Slack configuration.


### Slack HTML Investigation Report

The existing `POST /api/cases/{case_id}/slack` request and response are unchanged. The server generates a complete, sanitized HTML report from its stored `CaseAuditResult`; it excludes identities, resource IDs, free-form reasons, raw evidence, and evidence paths. Evidence references and known operation/system labels remain available. No case data is accepted from the browser.

The webhook message contains exactly: `EraSight — Investigation Report`, the case overview (ID, deletion status, derived severity and its qualification), then a link to the full HTML report. The report is uploaded through Slack's external file-upload API, shared with the configured channel, and linked using the private Slack file permalink. Slack access controls apply; no public file URL or local path is generated. Slack may also display its file-share message when the upload is finalized.

In the ignored root `.env`, configure `SLACK_BOT_TOKEN` with `files:write` and `files:read` scopes, plus `SLACK_REPORT_CHANNEL_ID` for **the same channel as the existing webhook**. Invite the bot to that channel and reinstall the Slack app after adding scopes. Retain `SLACK_WEBHOOK_URL`. None of these values belong in frontend variables. `/api/session` reports Slack as configured only when all required settings are present and syntactically valid; Slack validates scopes and membership during upload.

The upload must complete and return a safe, non-public Slack permalink before the existing Incoming Webhook is posted. Failure returns the existing safe error responses; the server does not fall back to a nonexistent download or claim success. If the upload succeeds but a later step fails, a file may already be visible in the channel: inspect Slack before retrying to avoid duplicates. There are no automatic retries.


The session response advertises `slack_report_format: "html-v1"`. The frontend checks it before posting a case; a missing or different format requires a backend restart and blocks older text-only senders. The backend loads root `.env` once at startup, resolved relative to `code/server.py`, with process environment variables taking precedence. Restart the API after editing server settings; refreshing Vite alone does not reload Python modules or server credentials.
