**Audited baseline:** `ff03e5f14d3937d453a12e43bdc9368a1981f5c0`

**Audit date:** 2026-10-25

## Executive verdict

**B — materially sound and fail-closed, with a safe general remediation applied, but not capable of reproducing every public label from eligible participant evidence.**

This letter grade is an audit shorthand: A would require no unresolved evidence/label discrepancy; B permits independently explained participant-data limitations or specification/label conflicts; C would indicate material correctable production defects; D would indicate unsafe or benchmark-compromising behavior. The repository does not define an official A–D rubric.

The baseline was conservative and secure, but it discarded valid workflow lineage when more than one action appeared in a report batch or when interleaved workflows required two independent temporal anchors. The smallest safe patch recovers fourteen exact canonical steps without reading labels in prediction code, weakening cutoffs, trusting activity outcomes, or adding case/resource exceptions. Eight canonical resources remain impossible at their audit cutoffs (three globally absent, five post-audit only), four canonical steps remain unlinked in two globally interleaved cohorts, and four grounded steps remain intentionally emitted despite their omission from canonical labels.

## Evaluator contract, independently traced

`code/evaluate.py`:

- compares status literally;
- parses `steps_json` with no normalization or duplicate suppression;
- compares ordered positions using `zip(expected, actual)`;
- adds six incorrect fields for every missing expected position;
- ignores extra actual positions in the field denominator, although extras fail step-count and exact-sequence accuracy;
- uses six scored fields (`phase`, `operation`, `state`, `system_id`, `resource_id`, `evidence_id`); `step_no` is not a field-accuracy component.

The supplemental diagnostic uses a `Counter` over those six-field tuples. Duplicate tuples therefore count with multiplicity. Neither clean run contained duplicate predicted tuples.

## Patch diagnosis and design

### Root cause 1: multi-action report batches

The baseline `_unique_report_anchor()` rejected a near-report batch whenever it contained more than one destructive action. Cases 06, 08, and 10 each contain exactly one account action plus a downstream action whose resource is independently linked to the subject. Each participating event is compatible with exactly one peer request.

**Patch:** `_anchored_report_account()` accepts the account only when all those conditions hold. Reported outcomes are ignored. Ambiguous peer windows and batches without an independent anchor still fail closed.

### Root cause 2: interleaved cadence chains

A single cadence edge is unsafe because global workflows overlap. Cases 18, 20, 22, 23, 26–29 have two or more subject-linked downstream resources in a coherent scheduling chain.

**Patch:** `_account_from_causal_chain()` requires an account-to-analytics dependency plus at least two independently evidenced, cadence-aligned resources. `_account_from_evidence_chain()` requires an exact account-to-anchor cadence plus at least two independently evidenced chain resources. Both reject more than one compatible account rather than ranking users or using input order. Activity outcomes are not state proof and are no longer used to select analytics lineage.

Synthetic regressions cover positive chains, insufficient evidence, unanchored batches, overlapping peers, and outcome-independence in `code/tests/test_workflow.py`.

## Security, leakage, and non-regression findings

- Prediction modules do not import evaluation diagnostics or canonical outputs.
- No case IDs, canonical resources, expected answers, or evidence IDs were added to production logic.
- Authorization classification, identity resolution, cutoff filtering, evidence provenance, contradiction rejection, and fail-closed validation remain intact.
- No post-audit evidence is admitted.
- No activity outcome is used as final-state proof.
- Status remains 32/32; there are no observed sample regressions.
- Security/workflow/observability targeted tests pass.
- The full suite has one pre-existing packaging/preflight failure because committed root `output.csv` is a stale invalid 518-row artifact; it is byte-identical to the audited baseline and was not represented as a valid regenerated output.
- Runtime is Python 3.11.2, not the requested Python 3.12. No API key or Tesseract executable was available; local RapidOCR supplied deterministic image extraction.

## Final decision

The patch is safe to retain. It improves evidence-backed recall substantially while preserving precision and every security boundary tested. A claim of 100% reproducibility would be false: eight canonical resources are unavailable at their cutoffs, two cases remain identity-ambiguous, and two canonical sequences omit specification-relevant grounded resources. Those limitations require participant-data corrections or evaluator-label corrections, not weaker production controls.
